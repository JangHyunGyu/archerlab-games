## 1. 게임 개요

스무고개는 사용자가 질문을 입력하고 AI의 예·아니오 답변으로 숨겨진 단어를 맞히는 웹게임이다. 서버가 정답을 고르고 사용자가 맞힌다. 디시전 모델은 각 질문의 유효성과 답을 판정한다. 한국어와 영어로 각각 접속해 같은 규칙으로 플레이한다.

짧은 추리 게임을 즐기는 모바일·PC 사용자를 대상으로 한다. 질문이 쌓일수록 가능한 답을 좁히는 과정과 적은 기회로 정답을 찾는 데 재미를 둔다. 화면은 밤의 탐정 서재를 모티프로 삼아 깊은 잉크색, 따뜻한 종이, 황동 세부 장식으로 구성한다. 봉인된 정답 문서와 20개의 눈금을 게임의 대표 시각 요소로 사용한다.

| 항목 | 기획 |
| --- | --- |
| 장르 | 자연어 질문 기반 추리 게임 |
| 플랫폼 | 모바일·PC 웹 |
| 출시 언어 | 한국어·영어, 각각 독립된 게임 페이지 |
| 한 판 목표 시간 | 3~5분. 실제 플레이 후 조정 |
| 판단 모델 | Microsoft-Decision-1 우선, 모델별 호출부 분리 |
| 정답 공급 | 매일 200개 개념, 각 개념의 한국어·영어 이름과 동의어 |
| 출제 순서 | 사용자에게 한 번도 출제하지 않은 개념만 추려 무작위 순서로 배정, 이후 순서대로 사용 |
| 저장소 | Cloudflare D1의 게임 전용 테이블 |
| 핵심 규칙 | 질문과 정답 제출을 합쳐 20회, 힌트 없음 |
| 랭킹 | 개인 최고 연속 성공 횟수, 동률이면 해당 기록의 총 사용 기회가 적은 순 |

## 2. 요구사항과 출시 범위

이번 요청의 필수 조건은 `archerlab-games` 아래에 추가할 스무고개 게임, 디시전 모델 사용, 한국어·영어 페이지 제공이다. 이번 산출물은 구현에 사용할 기획서와 문구 명세다.

판정 모델은 Microsoft-Decision-1을 우선 사용한다. 기존 기획의 힌트 없음, D1 전용 테이블, 매일 200개 교체와 폭넓은 단어 출제는 유지한다. 정답 제출도 1회를 쓰는 규칙, 새벽 4시 생성, 보류 기준, 보관 기간과 아래 수치 목표는 구현·평가 과정에서 조정할 기본값이다. 랭킹은 사용자 제안인 연속 성공 횟수를 채택하고 동률 처리·만료 규칙은 아래 설계안으로 둔다.

사용자별 출제 이력은 날짜가 바뀌어도 유지한다. 같은 사용자에게 한 번 배정한 정답 개념은 성공·실패·포기 여부와 관계없이 다시 출제하지 않는다. 매일 바뀌는 공통 후보 목록과 사용자별 누적 중복 방지를 별도로 관리한다.

| 1차 출시 포함 | 후속 검토 |
| --- | --- |
| 한국어·영어 독립 페이지와 게임 중 언어 전환 | 다른 언어 추가 |
| 자연어 질문, 예·아니오 판정, 정답 제출, 포기 | AI가 사용자 정답을 맞히는 역방향 모드 |
| 남은 기회·기록·결과, 이어 하기, 최고 연속 성공 랭킹 | 계정 연동, 주간·시즌 랭킹, 친구 대전 |
| 매일 200개 정답 생성·검증·교체 | 난이도·분야 선택, 추가 게임 모드 |
| 오류 복구, 호출·비용 제한, 모바일 대응 | 결과 공유 이미지, 장기 업적 |

초기 버전에 힌트, 광고 보상, 자유 대화 기능은 넣지 않는다. 로그인 없이 시작하며 오프라인에서는 기록을 읽을 수 있지만 새 질문과 정답 판정에는 연결이 필요하다.

## 3. 한 판의 진행

1. 진행 중인 판이 있으면 복귀한다. 없으면 현재 활성 정답 200개에서 해당 사용자의 누적 출제 이력을 제외하고 처음 만든 무작위 순서의 다음 개념을 선택한다.
2. 정답 배정, 누적 출제 이력 기록, 순서 위치 이동과 세션 생성을 함께 확정한다. 정답 이름, 의미, 특징, 인정할 표현은 게임 세션에 복사해 고정한다.
3. 사용자가 질문을 입력하면 서버가 Microsoft-Decision-1에 판정을 요청한다.
4. 판정 가능한 질문에는 예 또는 아니오를 표시하고 기회 1회를 차감한다.
5. 사용자는 언제든 정답 제출 모드로 전환해 단어를 입력할 수 있다.
6. 정답이면 즉시 성공한다. 오답이면 기회 1회를 쓰고 이어서 진행한다.
7. 20번째 행동이 정답이면 성공하고, 그렇지 않으면 실패한다. 종료 후 정답과 기록을 공개한다.

20회에는 질문과 정답 시도가 모두 포함된다. 질문 20회 뒤에 별도의 최종 제출 기회를 주지 않는다. 힌트 버튼, 힌트 데이터, 광고를 통한 힌트 제공은 넣지 않는다.

질문 모드에서 정답 이름을 물어 예를 받아도 성공 처리하지 않는다. 정답 제출 모드에서 맞혀야 성공한다. 마지막 기회에는 이 규칙을 다시 안내한다. 다시 하기는 한 번도 출제하지 않은 다음 개념으로 새 세션을 만든다. 다음 게임의 분야나 단어를 미리 알려주지 않는다. 더 출제할 개념이 없으면 새 목록을 기다리며 연속 성공 기록을 유지한다.

예를 들어 정답이 펭귄이면 동물인지, 새인지, 날 수 있는지를 차례로 물어 예·예·아니오를 받은 뒤 정답 제출 모드로 펭귄을 입력한다. 이 경우 4회를 사용하고 성공한다. 영어 페이지도 같은 정답 개념과 규칙을 적용한다.

## 4. 질문과 정답 판정

| 입력 또는 상황 | 처리 | 기회 사용 |
| --- | --- | --- |
| 의미가 분명하고 사실로 판단 가능한 질문 | 예 또는 아니오 | 1회 |
| 복수의 독립 질문을 한 번에 입력 | 질문을 나눠 입력하도록 안내 | 없음 |
| 주관적이거나 정답 자료가 부족한 질문 | 판정 보류 | 없음 |
| 같은 질문 반복 | 정규화한 원문이 같은 경우 이전 결과 재사용 | 없음 |
| 정답 제출 | 서버에서 정답·동의어와 비교 | 1회 |
| API 장애, 응답 형식 오류, 시간 초과 | 실패 안내 후 재시도 | 없음 |
| 종료된 게임에 추가 입력 | 접수하지 않음 | 없음 |

단순한 질문 표현만으로 정답 제출 모드를 자동 변경하지 않는다. 사용자가 선택한 입력 모드를 기준으로 처리해 의도하지 않은 승패 판정을 막는다.

정답 비교는 앞뒤 공백과 문자 정규화, 등록된 동의어를 기준으로 한다. 부분 문자열 일치나 무조건적인 유사도 판정은 사용하지 않는다. 상위 개념, 다른 종, 이름이 비슷한 사물을 잘못 정답으로 인정하지 않아야 한다. 띄어쓰기·오탈자 허용 범위는 한국어 사례를 모아 별도로 정한다.

최초 버전은 한국어 Unicode NFC 정규화와 앞뒤 공백 제거, 영어 대소문자 통일을 적용한다. 영어 단복수·관사·별칭과 한국어 띄어쓰기 변형은 검증한 동의어로 등록한다. 단어 내부 공백이나 구두점을 일괄 삭제하지 않는다. 한국어 페이지에서 `penguin`, 영어 페이지에서 `펭귄`을 제출해도 동일 개념의 등록 동의어면 정답으로 인정한다. `펭귄`에 `새`를 제출하면 오답이다.

한영 혼합 질문도 의미가 분명하면 판정한다. 부정 의문문, 이중 부정, 비교 대상이 빠진 표현은 답의 의미가 모호할 경우 다시 묻도록 안내하고 기회를 보존한다. 모델이 질문을 임의로 번역·수정한 뒤 다른 뜻으로 답하지 않도록 평가한다. 다른 언어의 질문이나 의미만 비슷한 질문까지 무료 중복으로 판정하는 기능은 초기 범위에서 제외한다.

## 5. 출제할 단어의 범위

사용자는 별도 카테고리 선택 없이 모든 분야의 단어를 만난다. 내부 분류는 생성 편중 방지와 통계에 사용한다.

동물, 식물, 음식, 생활용품, 도구, 장소, 직업, 인물, 캐릭터, 작품, 자연현상, 과학 용어, 추상적인 개념 등을 후보로 허용한다. 익숙한 단어를 중심으로 구성하되 특정 분야의 고정 목록으로 제한하지 않는다.

출제 가능 여부는 다음 기준으로 판단한다.

- 하나의 의미나 대상을 특정할 수 있는 단어
- 예·아니오 질문으로 구분할 만한 특징이 있는 단어
- 검증 가능한 기본 사실을 확보할 수 있는 단어
- 정답 이름과 동의어의 경계가 분명한 단어

동음이의어는 단어와 의미를 함께 저장한다. 인물과 작품은 공식 이름과 널리 쓰는 별칭을 기록한다. 추상 개념도 허용하지만, 개인의 가치 판단이 필요한 질문은 보류한다. 조사·어미·임의의 문자열, 실체가 확인되지 않은 생성 결과는 일반 출제에서 제외한다.

매일 200개 안에서는 같은 대상과 중복 표현을 제거한다. 공통 목록을 만들 때도 최근 7일간 포함한 대상을 우선 피한다. 이 7일은 후보 목록을 다양하게 구성하는 기본값이며 사용자별 재출제 금지 기간이 아니다. 사용자에게 이미 출제한 개념은 기간 제한 없이 제외한다. 다른 사용자에게 같은 개념을 출제하는 것은 허용한다.

한국어·영어 목록을 따로 200개씩 만들지 않고 공통 `concept_id` 200개를 만든다. 각 개념에 `ko`·`en` 이름, 의미 설명, 동의어와 같은 사실을 담은 자료를 붙인다. 예컨대 `animal.penguin`은 `펭귄`과 `penguin`을 연결한다. 사과라는 과일과 Apple이라는 회사는 별도 개념이며 서로의 동의어가 될 수 없다.

`concept_id`는 날짜별 생성 결과에서 새로 부여하지 않고 공통 개념 목록에서 찾아 재사용한다. 한영 이름·동의어·의미가 같은 대상을 서로 다른 ID로 등록하지 않도록 생성 후보를 대조한다. 같은 개념을 새 ID로 만들면 재출제 방지가 무효가 되므로 개념 식별 검사는 활성화 전 필수 조건이다.

한쪽 언어의 이름·의미·사실 검증이 빠진 후보는 활성 목록에서 제외한다. 초기에는 양쪽 언어권에서 이름과 특징이 비교적 익숙한 대상을 우선한다. 문화권별 난이도 차이는 실제 정답률로 확인하며 이름만 번역했다고 난이도가 같다고 간주하지 않는다.

## 6. 모델의 역할

### Microsoft-Decision-1의 게임 중 판단

Microsoft-Decision-1은 정해진 선택지에 확률을 반환하며 예·아니오와 분류 판정을 지원한다. 스무고개의 질문 유효성·근거·참거짓 판단에 사용하는 안으로 잡는다. 한국어·영어 게임 질문에서의 정확도와 응답 속도는 별도로 평가한다. [Microsoft 모델 안내](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/how-to/use-foundry-models-microsoft-decision).

초기 연동은 OpenRouter 경유, 모델 ID는 `microsoft/microsoft-decision-1`로 계획한다. Microsoft Foundry 직접 호출도 지원 가능한 선택지다. Foundry 경로는 `<resource-endpoint>/providers/microsoft/v1/systemone`이며 요청의 `model`에는 실제 배포 이름을 넣는다. 두 경로의 인증·요청·응답 검사는 호출 모듈 안에서 분리하고 실제 연결은 구현 단계에서 검증한다. [OpenRouter 모델 페이지](https://openrouter.ai/microsoft/microsoft-decision-1), [Foundry 호출 방식](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/how-to/use-foundry-models-microsoft-decision#call-the-decision-api).

모델 ID·제공 경로·프롬프트 버전·임계값은 서버 설정으로 관리한다. 모델 ID가 같아도 제공사가 가중치를 갱신할 수 있으므로 고정 평가 질문을 주기적으로 재검사한다. Jev는 필요할 때 비교 평가할 대체 후보로 남기며 게임 도중 검증 없이 자동 전환하지 않는다. 모델별 확률에 같은 임계값을 그대로 적용하지 않는다.

서버가 보내는 정보는 고정된 정답의 의미·사실 카드, 사용자 질문, 필요한 이전 판정이다. 질문 유효성, 자료 충분성, Y/N 여부를 독립된 질문으로 요청하고 서버가 결과를 조합한다. Noul은 예일 확률을 반환하고, Choice는 미리 정의한 선택지 중 하나를 반환한다. 같은 요청에 넣은 판단들은 서로의 결과를 참조하지 않는다.

게임용 판정 항목은 다음처럼 나눈다. 아래 이름과 결과 조합은 이 게임의 설계이며 모델의 기본 제공 기능 이름이 아니다.

| 항목 | 유형 | 판단할 내용 |
| --- | --- | --- |
| `question_kind` | Choice | 단일 사실 질문 / 복수 질문 / 주관적 질문 / 불명확한 입력 / 규칙 변경 지시 |
| `supported_by_facts` | Noul | 고정 사실 자료로 이 질문을 판정할 근거가 충분한가 |
| `answer_yes` | Noul | 사용자 질문의 명제가 정답의 사실과 일치하는가 |

한 요청의 세 항목은 같은 자료만 보고 판단한다. 서버는 단일 사실 질문이고 근거가 충분할 때만 `answer_yes`를 채택한다. 임계값을 `T_no < T_yes`로 두고 `p <= T_no`면 아니오, `p >= T_yes`면 예, 사이는 보류로 처리한다. 유효성·근거 판정에도 별도 기준을 두며 정확한 값은 한영 평가 후 결정한다. 과거 답변은 일관성 확인용이고 검증된 사실보다 우선하지 않는다. 사실과 과거 답변이 충돌하면 보류하고 품질 검토 대상으로 남긴다.

확률 0.5를 기준으로 무조건 Y/N을 결정하지 않는다. 사실 카드의 정보가 충분한지 먼저 확인하고 실제 한국어·영어 평가 결과로 정한 임계값을 적용한다. 확신도는 실제 정답률을 보장하지 않으므로 화면에 정확도 수치로 표시하지 않는다.

예·아니오, 판정 보류와 오류 안내는 게임이 정해진 문구로 표시한다. 사용자 질문은 판단 대상 데이터로 취급하고, 질문 안의 지시로 정답이나 게임 규칙을 변경하지 않는다.

### 생성형 모델: 하루 정답 목록 작성

디시전 모델과 별도의 생성형 모델이 단어와 사실 카드를 만든다. 모델은 한국어 품질, 구조화 응답 지원, 비용을 비교한 뒤 선정한다. 이번 기획에서 특정 생성 모델은 확정하지 않는다.

생성 결과에는 단어, 의미 설명, 분야, 동의어, 기본 특징, 난이도 제안을 포함한다. 모델이 작성한 사실을 곧바로 검증된 사실로 간주하지 않는다. 인물·작품·전문 용어처럼 오류 가능성이 있는 항목은 신뢰할 수 있는 자료와 대조하고, 확인이 어려우면 후보에서 제외한다. 출처 링크가 실제로 해당 사실을 뒷받침하는지도 확인한다.

한국어·영어 명칭과 설명을 함께 생성하고 번역 간 의미가 같은지 검사한다. 플레이 중에는 별도 번역 모델이나 생성형 모델을 호출하지 않는다. 정답·동의어 비교는 서버 코드가 맡고 안내 문구는 [SCENARIO.md](SCENARIO.md)의 고정 문자열을 쓴다. 평가가 끝나기 전까지 한국어·영어 판정 품질은 미검증 상태다.

## 7. 매일 200개 생성과 교체

Cloudflare Cron Triggers로 한국 시간 매일 새벽 4시에 생성 작업을 시작한다. Cron은 UTC 기준이므로 표현식은 `0 19 * * *`다. 새벽 4시는 생성 시작 시각이며 교체 시각은 양쪽 언어를 갖춘 200개의 검사가 완료된 시점이다. [Cron Triggers 시간 기준](https://developers.cloudflare.com/workers/configuration/cron-triggers/).

1. 한국 시간 기준 날짜를 작업 키로 만들고, 해당 날짜의 완료 작업이 있으면 종료한다.
2. 작업 소유권을 확보하고 준비 상태의 새 묶음을 만든다. 중복 실행은 기존 진행 상태를 확인한다.
3. 분야를 분산해 25개 안팎씩 생성하고 중간 결과를 저장한다.
4. 형식, 의미, 한영 동의어, 번역 일치, 중복, 사실 카드의 품질을 검사한다.
5. 탈락한 항목 수만큼 보충하되 재시도 횟수와 비용 상한을 적용한다.
6. 사용 가능한 정답이 정확히 200개일 때만 해당 묶음을 완료 상태로 만든다.
7. 활성 묶음 ID를 한 번에 바꿔 신규 게임에 적용한다.

생성과 검사는 활성 목록 밖에서 수행한다. D1 트랜잭션 안에서 외부 모델 응답을 기다리지 않는다. 최종 완료 처리와 활성 ID 전환은 원자적으로 실행하고, 오래된 작업이 나중에 끝나 최신 목록을 덮어쓰지 않도록 날짜와 현재 상태를 검사한다.

실패하면 기존 활성 목록을 계속 사용한다. 실패한 작업은 저장된 진행 상태부터 이어서 재시도하며, 무제한으로 모델을 호출하지 않는다. 최초 운영 때는 검사를 통과한 초기 200개를 미리 준비한다. 활성 목록이 전혀 없으면 게임 시작을 잠시 막고 재시도 가능한 상태를 반환한다.

생성이 실행 환경의 제한 시간을 넘을 가능성이 있으면 Cloudflare Workflows 또는 Queues로 작업을 나눈다. Cron은 작업 시작을 담당하고, 분할 작업은 완료·재시도 상태를 기록한다. 실제 실행 방식은 구현 시 런타임 제한과 측정 시간으로 결정한다.

현재 공용 Worker에는 Bubbly Lab 정리 작업용 `30 19 * * *`가 있다. 신규 생성 작업을 추가할 때 기존 스케줄을 유지하고 `scheduled` 처리에서 이벤트의 cron 값으로 작업을 분리한다. 기존 핸들러는 모든 스케줄에서 정리 작업을 호출하므로 스케줄 문자열만 추가해서는 안 된다.

### 사용자별 순서와 누적 중복 방지

공통 목록은 하루 200개를 준비하되 각 사용자에게는 그중 아직 출제하지 않은 개념만 제공한다. 따라서 이용 가능한 개수는 사용자마다 다르고 최대 200개다. 남은 개념을 서버에서 한 번 섞어 저장한 뒤 다음 위치를 차례로 사용한다. 모든 사용자가 같은 순서로 정답을 받지 않으며 전체 목록과 순서는 브라우저에 보내지 않는다.

| 상황 | 출제 처리 |
| --- | --- |
| 새 묶음에서 첫 판 시작 | 누적 출제 개념 제외 후 남은 개념의 무작위 순서 생성 |
| 다음 판 시작 | 저장한 순서의 다음 미출제 개념 배정 |
| 성공·실패·포기·만료 | 해당 개념은 계속 사용 완료 상태로 유지 |
| 새로고침·연결 끊김·다른 탭·언어 전환 | 같은 진행 중 세션 복구, 새 개념 배정 없음 |
| 자정 경과·정답 목록 갱신 | 누적 출제 이력 유지. 진행 중 판은 고정 정답으로 끝내고 다음 판부터 활성 묶음 사용 |
| 더 출제할 개념 없음 | 새 목록 활성화까지 신규 판 시작 대기, 연속 성공 기록 유지 |
| 일별 생성 실패 | 기존 목록의 남은 미출제 개념만 사용, 이미 쓴 단어로 수량을 채우지 않음 |

사용 완료 시점은 서버가 세션을 생성해 정답을 배정한 때다. 사용자 화면에 정답이 공개되는 때나 성공한 때까지 미루지 않는다. 응답이 유실되면 이미 생성한 세션에 복귀한다. 같은 시작 요청의 재전송이나 동시 탭 요청은 동일 세션을 반환하고 출제 이력·순서를 두 번 소비하지 않는다.

출제 이력 등록과 세션 생성이 함께 실패하면 순서도 되돌린다. 이미 확정한 세션의 질문 판정만 실패했을 때는 같은 정답으로 재시도한다. 활성 묶음이 바뀌면 이전 묶음의 남은 순서를 버리고 새 묶음에서 누적 이력을 제외한 순서를 만든다. 미출제 단어가 없어 대기 중일 때는 진행 중 세션을 만들지 않으므로 24시간 만료도 시작하지 않는다.

재출제 금지는 서버의 동일 플레이어 ID를 기준으로 보장한다. 현재 익명 설계에서는 같은 브라우저의 저장된 플레이어 토큰으로 이어진다. 브라우저 데이터를 삭제하거나 새 기기에서 다른 ID를 만들면 같은 사람인지 알 수 없다. 여러 기기와 재방문까지 사람 단위로 보장하려면 계정 연동이 필요하다.

## 8. D1 전용 테이블 설계

기존 게임과 이름이 충돌하지 않도록 `twenty_questions_` 접두어를 사용한다. 아래는 논리 설계이며, 실제 마이그레이션은 구현 단계에서 작성한다.

| 테이블 | 주요 데이터 | 목적 |
| --- | --- | --- |
| `twenty_questions_answer_batches` | ID, 한국 기준 날짜, 상태, 유효 정답 수, 생성 모델·버전, 비용, 재시도 수, 작업 소유권·만료 시각 | 일별 생성 작업과 재실행 관리 |
| `twenty_questions_concepts` | 안정된 `concept_id`, 대표 이름·의미 키, 한영 동의어, 중복 대조 정보 | 날짜를 넘겨 같은 개념을 식별 |
| `twenty_questions_answers` | ID, 묶음 ID, `concept_id`, 분야, `locales.ko/en` 이름·설명·동의어 JSON, 사실 카드 JSON, 언어별 검증 상태와 근거 | 한영 이름을 갖춘 정답 200개 저장 |
| `twenty_questions_settings` | 설정 키, 값 | 현재 활성 묶음 ID와 운영 설정 |
| `twenty_questions_sessions` | ID, 플레이어·연속 도전 ID, 한영 정답 스냅샷, 묶음 ID, 시작 언어, 사용 횟수, 상태, 버전, 만료 시각, 랭킹 반영 여부 | 진행 중인 게임과 정답 고정 |
| `twenty_questions_turns` | 세션 ID, 요청 ID, 입력 모드, 입력 원문·언어, 판정 코드, 확률, 차감 여부, 모델·프롬프트 버전, 비용 | 질문 기록과 중복 요청 방지 |
| `twenty_questions_players` | 익명 플레이어 ID, 인증 토큰 해시, 표시 이름, 활성 도전 ID | 여러 판의 동일 플레이어 식별 |
| `twenty_questions_player_decks` | 플레이어·묶음 ID, 섞은 개념 ID 순서, 다음 위치, 버전 | 미출제 개념을 섞은 순서대로 배정 |
| `twenty_questions_seen` | 플레이어 ID, `concept_id`, 최초 배정 시각, 최초 세션 식별값 | 기간 제한 없는 사용자별 출제 이력 |
| `twenty_questions_streaks` | 도전 ID, 플레이어 ID, 연속 성공 수, 누적 사용 기회, 상태, 마지막 결과 세션 ID | 연속 성공 누적과 중복 반영 방지 |
| `twenty_questions_records` | 플레이어·규칙 버전, 최고 연속 성공 수, 해당 총 사용 기회, 달성 시각, 검증 상태 | 랭킹용 최고 기록 보관 |

생성 날짜와 세션별 요청 ID에는 중복 방지 제약을 둔다. 같은 묶음 안의 정답은 단어와 의미를 정규화한 키로 중복을 검사한다. 활성 묶음과 세션 조회에 필요한 인덱스를 둔다.

출제 이력의 `(player_id, concept_id)`와 순서의 `(player_id, batch_id)`에 고유 제약을 둔다. 한 플레이어에게 진행 중인 세션은 하나만 허용한다. 서버가 다음 개념을 배정할 때 순서 위치·출제 이력·활성 세션을 같은 트랜잭션으로 확정하고 경합하면 먼저 확정된 세션을 조회한다.

초기 보관 기본값은 이전 정답 묶음 30일, 종료된 게임과 질문 로그 30일, 미완료 세션 유효기간 24시간이다. 진행 중 세션은 정답 스냅샷을 사용하므로 목록 교체 후에도 같은 기준으로 판정한다. 삭제 작업은 활성 묶음과 유효한 참조를 보호한다. 오래된 통계가 필요하면 원문 질문 없이 집계값만 남긴다.

랭킹용 최고 기록과 성공 횟수·총 사용 기회·규칙 버전 등 검증 요약은 원문 로그와 분리해 유지한다. 질문 로그의 30일 정리로 개인 최고 기록이 삭제되거나 진행 중 연속 도전이 끊기지 않게 한다.

공통 개념 ID와 사용자별 출제 이력도 30일 로그 정리 대상에서 제외한다. 동일 플레이어 ID가 유지되는 동안 출제 이력을 보관하며 날짜·묶음·연속 도전의 변경으로 지우지 않는다. 사용 완료 순서는 활성 세션의 참조가 끝나면 정리할 수 있지만 출제 이력은 남긴다. 최초 세션 식별값은 감사용 값으로 보관하고 원문 세션 삭제가 출제 이력을 연쇄 삭제하지 않도록 한다.

## 9. 서버와 API

게임 화면 → 게임 서버 → D1 및 OpenRouter → 판정 검증 → 화면 표시 순서로 동작한다. 현재 저장소는 HTML·JS 게임 페이지와 `game-api-entry.js`의 공용 Worker, `archerlab_db` D1을 사용한다. 제안안은 게임 모듈을 별도 파일로 만들고 공용 Worker에 전용 경로를 연결하는 것이다. 정답 데이터는 정적 게임 자산에 포함하지 않는다.

현재 공용 API 기본 주소는 `https://game-api.yama5993.workers.dev`다. 아래는 이 API 주소에 붙일 제안 경로다. 포털과 같은 출처의 `/api/...` 프록시는 현재 없는 것으로 보고 추가 구현을 전제하지 않는다. 운영 주소는 설정값으로 관리한다.

| 제안 경로 | 처리 |
| --- | --- |
| `POST /twenty-questions/games` | `{ locale, requestId }`로 진행 중 판 복구 또는 미출제 개념 배정·이력 기록·세션 생성 |
| `GET /twenty-questions/games/:id` | 본인 게임의 공개 상태와 기록 조회 |
| `POST /twenty-questions/games/:id/questions` | `{ text, locale, requestId, expectedVersion }`로 질문 판정 |
| `POST /twenty-questions/games/:id/guesses` | 같은 공통 필드로 정답 제출과 승패 판정 |
| `POST /twenty-questions/games/:id/give-up` | 요청 ID·버전을 확인하고 포기 처리 후 정답 공개 |
| `GET /twenty-questions/leaderboard` | 현재 규칙 버전의 최고 기록과 본인 순위 조회 |
| `PATCH /twenty-questions/profile` | 인증된 플레이어의 표시 이름 변경 |

API 키는 서버 비밀 설정에 저장한다. 게임 종료 전에는 정답·동의어·사실 카드·모델 요청 원문을 클라이언트에 보내지 않는다. 세션 소유권을 확인하고, 요청 ID와 세션 버전으로 재전송과 동시 입력이 기회를 두 번 차감하지 않도록 한다.

AI 판정이 끝난 뒤 세션 상태를 다시 확인하고 기록·횟수·승패를 함께 확정한다. 이미 끝난 게임이나 오래된 버전의 판정은 반영하지 않는다. 질문 길이, 호출 빈도, 일별 모델 비용에 상한을 둔다. 기회를 차감하지 않는 보류·오류 요청에도 호출 제한은 적용한다.

익명 소유권은 서버가 발급한 충분히 긴 비밀 토큰으로 확인하고 서버에는 토큰의 해시를 저장한다. 플레이어 토큰은 여러 판의 연속 기록을 연결하고 세션 토큰은 한 판의 복귀를 맡는다. 토큰은 인증 헤더로 전달하며 세션 ID만 아는 사용자는 기록을 조회하지 못한다. API는 허용한 포털 출처만 CORS로 허용하고 개인별 응답은 `Cache-Control: no-store`로 반환한다. 브라우저에는 플레이어 토큰·진행 중 세션·공개 기록을 저장하고 종료·만료 후 해당 세션 토큰만 지운다. 사용자 입력은 HTML로 실행하지 않고 텍스트로 렌더링한다.

API 응답은 `status`, `resultCode`, `turnsUsed`, `remaining`, `version`, 공개 기록을 담는다. `answer`와 의미 설명은 종료된 게임에서만 반환한다. 상태는 `active`, `won`, `lost`, `given_up`, `expired`로 구분한다. 오류 안내는 HTTP 상태와 안정된 오류 코드로 매핑하고 모델의 원문 오류를 그대로 노출하지 않는다.

초기 제한 제안은 질문 200자, 정답 80자, 세션당 동시 판정 1개, 판정 요청 분당 20회·세션당 60회다. 길이는 Unicode 코드 포인트 기준으로 서버에서 검사한다. 모델 대기 시간은 8초를 초기 상한으로 두고 측정 후 조정한다. 제한·시간 초과는 기회를 차감하지 않는다. 세션 시작에는 별도 발급 제한을 두어 새 세션으로 호출 제한을 우회하지 못하게 한다. 전체 일별 비용 상한은 공개 전 운영 설정으로 확정한다.

응답을 받지 못한 클라이언트는 상태 조회로 처리 여부부터 확인한다. 재전송에는 같은 요청 ID를 사용하고 내용이 다른데 요청 ID만 같으면 거부한다. 서버에서 이미 확정한 질문을 통신 오류 때문에 다시 차감하거나 임의로 되돌리지 않는다. 언어 전환·탭 중복·포기와 판정이 겹쳐도 세션 버전 조건으로 한 번만 확정한다.

미출제 개념이 없으면 시작 API는 `pool_exhausted` 코드와 새 목록 대기 상태를 반환한다. 세션·기회·실패 결과를 만들지 않고 서버가 새 목록을 활성화한 뒤 다시 시작할 수 있게 한다. 다음 목록의 완료 시각은 확정값으로 안내하지 않는다.

정답 목록 갱신으로 연속 성공 기록을 초기화하지 않는다. 성공 확정·세션 랭킹 반영 표시·연속 횟수 증가·최고 기록 갱신은 서버에서 원자적으로 처리한다. 클라이언트가 전송한 성공 횟수나 점수를 신뢰하지 않는다. 현재 공용 랭킹은 일반 게임을 점수·달성 시각 순으로 정렬하므로 스무고개의 동률 기준과 플레이어 식별을 그대로 처리하지 못한다. 게임 전용 랭킹 조회·갱신을 만들고 공용 랭킹 저장 경로에서 이 게임의 임의 점수 제출을 받지 않도록 한다.

## 10. 화면과 사용성

- 시작 화면: 게임 이름, 간단한 규칙, 시작 버튼
- 게임 화면: 남은 기회, 질문·답변 기록, 입력창, 질문·정답 제출 모드, 포기
- 결과 화면: 성공·실패, 정답과 의미, 사용 횟수, 질문 기록, 다시 시작
- 랭킹 화면: 순위, 표시 이름, 최고 연속 성공 횟수, 해당 총 사용 기회, 본인 기록

게임 화면에는 현재 연속 성공 횟수, 결과 화면에는 현재 기록과 개인 최고 기록을 표시한다. 성공 뒤 다시 하기는 같은 도전의 다음 판으로 진행한다. 실패 뒤 다시 하기는 연속 0회에서 새 도전을 시작한다.

고급 탐정 서재의 차분한 분위기로 구성하고 질문과 기록을 선명하게 읽을 수 있게 한다. 모델명이나 판정 확률 같은 구현 정보는 기본 게임 화면에 노출하지 않는다. 초기에는 정답의 분야를 공개하거나 선택하게 하지 않는다.

모바일 키보드가 열려도 입력창과 전송 버튼에 접근할 수 있어야 한다. 작은 휴대전화, 큰 휴대전화, 태블릿, 데스크톱의 가로·세로 화면을 확인한다. 터치 대상은 44 CSS 픽셀 이상으로 두고, 키보드 조작·포커스 표시·동작 줄이기 설정을 지원한다.

이번 기획서 작성에서는 기존 포털의 카드, 메뉴, 스타일, 순서를 변경하지 않는다. 게임 구현이 완료되기 전에는 포털에 실행 가능한 게임으로 등록하지 않는다.

### 아트 디렉션

디자인 방향은 비밀 단어가 봉인된 문서를 한 문제씩 해결하는 탐정 서재다. 게임 이름은 스무고개 / Twenty Questions를 유지한다. 첫 화면은 실제 책상 위 서류처럼 깊이와 재질을 느끼게 하고 플레이 화면은 질문 기록을 읽고 입력하는 데 집중한다. 인물 마스코트보다 봉인 문서·종이 기록·20개의 황동 눈금을 반복해 게임의 인상을 만든다.

배경과 함께 버튼·패널·탭·판정 도장·랭킹 휘장까지 전용 이미지 에셋으로 제작한다. 같은 원본 디자인에서 파생해 금속 모서리, 가죽 표면, 종이 두께, 광원 방향과 그림자 길이를 일치시킨다. 상용 게임의 완성도를 목표로 에셋 자체의 품질과 실제 조작 상태를 함께 검수한다.

서재의 밤 조명, 짙은 가죽 문서판, 두꺼운 종이와 무광 금속을 소재로 쓴다. 배경 책장은 초점을 흐리고 책등·장식·물건에 정답과 연결되는 정보를 넣지 않는다. 문서 봉인은 모든 문제에 같은 모양으로 사용한다. 캐릭터·정답 실루엣·분야별 배경을 자동 노출해 의도하지 않은 힌트를 주지 않는다.

20개 눈금은 남은 기회를 나타낸다. 정답에 가까워졌다는 정도나 모델 확신도를 표현하지 않는다. 보류·오류·무료 중복 응답에서는 눈금이 줄지 않는다. 현재 연속 성공 수는 별도 위치의 숫자로 표시해 20회 제한과 혼동하지 않게 한다.

데스크톱 시작 화면은 좌측 제목·행동 버튼과 우측 대표 이미지로 배치한다. 진행 화면은 폭 약 760~880 CSS 픽셀의 기록 영역을 중심에 두고 배경 서재가 가장자리에 남도록 한다. 작은 휴대전화는 대표 장식을 축소하고 기록·입력 영역에 높이를 배정한다. 모바일 키보드가 열리면 장식 영역을 접고 입력창·전송·남은 기회가 보이게 한다. 실제 화면은 대표 시안의 비율을 그대로 축소하지 않고 기기별로 재배치한다.

### 움직임과 소리

버튼 상태 변화는 120~180ms, 판정 표시는 180~240ms, 정답 문서 열림은 450~650ms를 초기값으로 잡는다. 입력 직후 대기 상태를 표시하며 정답 판정이 이미 끝났는데 분위기를 만들려고 응답을 지연하지 않는다. 기록 추가가 기존 기록의 스크롤 위치를 갑자기 바꾸지 않게 한다. 동작 줄이기 설정에서는 펼침·빛 이동을 생략하고 결과를 즉시 표시한다.

사운드는 전송·판정·정답 공개·연속 기록 갱신마다 촉감이 느껴지는 짧은 소리로 구성한다. 사용자가 허용한 기존 `archerlab-games` 게임의 효과음 파일을 우선 재사용한다. 판정은 짧고 선명하게, 정답 성공은 여러 소리가 순서대로 이어지는 보상 연출로 설계한다. 음악은 선택 사항이며 첫 조작 전에 자동 재생하지 않는다. 음소거해도 같은 정보를 얻을 수 있게 하고 실패에는 큰 경고음을 쓰지 않는다.

| 질문 전송 | 버튼 눌림, 입력 문장이 기록지에 안착, 대기 표시 | 눌림 소리와 짧은 이동음, 100~200ms |
| 질문 판정 예 | 예 도장이 눌렸다가 자리 잡음, 해당 행에 짧은 청록 강조, 눈금 1개 변경 | 가벼운 타격과 맑은 확인음, 180~300ms |
| 질문 판정 아니오 | 아니오 도장이 같은 강도로 자리 잡음, 해당 행만 적갈색 강조, 눈금 1개 변경 | 예와 구별되는 낮고 또렷한 단음, 180~300ms. 정답 실패음과 분리 |
| 정답 제출 성공 | 봉인 해제 → 정답 카드 펼침 → 짧은 황동 빛·입자 → 연속 숫자 증가 | 짧은 개봉 타격 → 상승음 → 기록 확정음. 전체 700~1,100ms |
| 정답 제출 오답, 기회 남음 | 제출 영역에 한 번의 작은 반동, 오답 표시, 기회 감소 후 즉시 재입력 | 둔탁하지만 짧은 거절음, 150~300ms |
| 최종 실패·포기 | 봉인이 풀리며 정답 공개, 현재 연속 기록 종료·최고 기록 보존 | 짧은 하강 마무리음, 400~800ms. 오답음과 중복하지 않음 |
| 개인 최고 기록 갱신 | 기록 숫자 확대 후 복귀, 휘장 가장자리에 한 번의 빛 | 성공음 뒤 200~400ms의 짧은 반짝임. 같은 갱신 이벤트에서 한 번 |
| 보류·무료 중복·통신 오류 | 상태 안내만 표시하고 기록·눈금 보존 | 보류·중복은 작은 중립음 또는 무음, 재시도 오류는 연속 경고음 없이 안내 |
| 랭킹 열기 | 명부 패널 등장과 본인 행 표시 | 짧은 열림음, 200~400ms |

정답 성공 연출은 타격·개봉·기록 증가의 강조 시점을 나눠 쾌감을 만든다. 서버 성공 응답 직후 첫 반응을 보여주고 전체 연출이 끝날 때까지 다음 조작을 불필요하게 잠그지 않는다. 개인 최고 기록을 갱신한 판은 성공 효과에 기록 강조를 덧붙이며 두 개의 긴 팡파르를 동시에 틀지 않는다.

질문에 대한 아니오는 정답 후보를 좁히는 유효한 결과다. 오답 제출·패배와 다른 소리를 사용하며 화면 전체를 흔들지 않는다. 보류·무료 중복·오류에는 기회 감소 효과를 재생하지 않는다. 전송 소리는 사용자 입력에 반응하지만 도장·성공·실패·기록 갱신 효과는 서버가 확정한 결과를 기준으로 재생한다.

### 재생 품질과 동기화

반복 효과는 앞 무음과 불필요한 긴 잔향을 줄이고 도장 타격 프레임에 소리의 시작을 맞춘다. 모바일 스피커와 이어폰에서 타격음이 들리면서도 고음이 날카롭지 않은지 청취한다. 성공 순간에는 배경음만 잠깐 낮춰 결과 소리가 드러나게 하고 전체 소리를 크게 올리는 방식에 의존하지 않는다. 최종 출력의 클리핑을 확인한다.

사운드 켜기·끄기 설정을 저장하고 BGM과 효과음의 음량을 따로 조정할 수 있게 한다. 중복 전송·새로고침·언어 전환으로 이전 성공 효과가 다시 울리지 않도록 결과 이벤트를 한 번만 소비한다. 비활성 탭에서는 새 효과를 쌓아두지 않으며 돌아왔을 때 과거 소리를 한꺼번에 재생하지 않는다. 오디오 로딩 실패는 게임 진행을 막지 않는다.

실제 단말에서 전송부터 판정까지, 연속 질문, 20번째 성공·실패, 최고 기록 갱신과 복귀 상황을 재생해 음원 겹침·지연·뒤늦은 소리를 검사한다. 동작 줄이기 설정에서는 반동·입자·빛 이동을 생략하고 같은 의미의 텍스트·도장을 표시한다. 소리를 끄면 별도의 시각 피드백만으로도 결과를 알 수 있어야 한다.

### 에셋 제작과 품질 기준

대표 이미지에는 봉인 문서와 책상 조명을 쓰고 PC 가로 구도와 모바일 세로 구도를 따로 검토한다. 모든 이미지 생성·편집은 선택 도구의 최고 품질과 최고 지원 원본 해상도를 사용한다. 실제 출력 크기를 기록하고 원본은 보존한다. 화면용 최적화 파일은 별도 파생본으로 관리하며 원본을 축소해 덮어쓰지 않는다.

버튼·패널·탭·눈금·판정 도장의 외형은 이미지 에셋으로 구성하고 문구·숫자·선택 상태는 별도 UI 계층에서 표시한다. 큰 화면 이미지 한 장에 조작부와 문구를 합쳐 넣지 않는다. 각 요소가 한영 전환·화면 크기·실제 서버 상태에 맞춰 동작하도록 한다. 시안의 가상 기록·예시 숫자는 운영 데이터로 사용하지 않는다. 공개 전 모든 정답 종류에서 같은 장식을 쓰는지도 검사한다.

| 전용 UI 에셋 | 필요한 상태·변형 | 제작·적용 기준 |
| --- | --- | --- |
| 주요 버튼 | 기본·마우스 올림·눌림·비활성·키보드 포커스 | 같은 황동 프레임의 밝기·눌림 깊이만 변화, 상태마다 크기·모양이 흔들리지 않음 |
| 문서 패널 | 기본·작은 확인창·결과 카드 | 모서리와 가운데를 나눠 늘려도 금속 선·종이 질감이 찌그러지지 않게 제작 |
| 질문/정답 탭 | 선택·비선택·포커스 | 같은 가죽·황동 재질, 라벨과 선택 표시를 함께 사용 |
| 판정 도장 | 예·아니오·보류의 문구 없는 바탕 | 실제 언어별 글자는 별도 표시, 테두리 모양도 구별 |
| 남은 기회 눈금 | 미사용·사용·마지막 기회 | 공통 눈금 에셋을 정확히 20개 배치하고 서버 확정 횟수만큼 상태 변경 |
| 기록 장식 | 1~3위 휘장·개인 최고 기록 표시 | 같은 선 굵기와 무광 금속, 과한 보석·왕관 장식 배제 |
| 아이콘 | 소리·랭킹·닫기·뒤로 가기 | 같은 규격과 광원으로 제작, 작은 화면의 실제 크기에서 형태 확인 |
| 봉인과 정답 문서 | 봉인·해제·펼침 | 같은 문서의 위치·크기 유지, 결과에 따른 단순한 상태 전환 |

같은 부품의 상태를 매번 별개 이미지로 생성하지 않는다. 확정한 기준 에셋을 수정해 형태를 유지한다. 투명 에셋은 실제 알파 채널로 보관하고 밝은 배경·어두운 배경 양쪽에서 흰 테두리와 잘린 그림자를 확인한다. 버튼 테두리·휘장·패널의 명암 방향이 서로 다르면 수정한다. 가짜 글자, 의미 없는 문양, 반복 무늬의 끊김, 들쭉날쭉한 모서리는 출시 전에 제거한다.

검수는 원본 확대와 실제 표시 크기를 모두 사용한다. 휴대전화에서 44 CSS 픽셀 이상의 조작 영역 안에 글자와 테두리가 자연스럽게 들어가야 한다. 버튼 이미지를 눌렀을 때 그림자 변화와 실제 클릭 반응의 시점이 일치해야 한다. 원본·파생본·상태별 파일의 출처와 버전을 기록하고 배경만 정교한 상태에서 UI를 임시 부품으로 남겨두지 않는다.

디자인 검수는 시작·진행·입력 대기·마지막 기회·성공·실패·포기 확인·이어 하기·목록 대기·랭킹 상태를 한국어와 영어로 진행한다. 과한 금속 광택이나 배경 질감으로 본문이 흐려지면 줄인다. 모바일에서 질문을 읽고 입력하는 화면을 우선 검수하고 배경 이미지 로딩 전에도 핵심 조작이 가능하게 한다. 기존 게임과 포털의 화면은 이 신규 게임 디자인 작업으로 변경하지 않는다.

### 페이지와 언어

| 구분 | 한국어 | 영어 |
| --- | --- | --- |
| 파일 | `twenty-questions/index.html` | `twenty-questions/index-en.html` |
| 공개 경로 | `/twenty-questions/` | `/twenty-questions/index-en` |
| 게임명 | 스무고개 | Twenty Questions |
| HTML 언어 | `ko` | `en` |
| 포털 진입 | 한국어 포털의 신규 게임 카드 | 영어 포털의 신규 게임 카드 |

두 페이지는 각 URL에서 전체 게임 화면을 제공한다. 영어 페이지를 한국어 페이지로 자동 이동시키지 않는다. 페이지 URL의 언어를 저장된 선호 언어나 브라우저 언어보다 우선한다. 사용자는 화면의 한국어·English 전환으로 원하는 페이지를 선택한다.

게임 중 전환해도 세션 ID·정답·사용 횟수·입력 모드·입력 중 문장·기록을 유지한다. 판정 중 전환 요청은 응답이나 상태 조회를 마친 뒤 적용한다. 이전 질문은 입력 원문 그대로 두고 예·아니오와 상태 안내만 현재 언어로 표시한다. 전환할 때 이미 끝난 질문을 재판정하지 않는다. 페이지를 다시 불러오면 저장한 세션으로 상태를 조회한다. 토큰은 URL에 넣지 않는다.

제목, 규칙, 입력 예시, 버튼, 상태·오류·결과, 포기 확인, 접근성 이름, 정답 의미 설명까지 한영을 제공한다. 화면에 출력할 키가 빠졌을 때 다른 언어를 조용히 섞지 않고 개발 검사에서 실패시킨다. 한국어의 정답 뒤 조사·서술어는 받침에 맞춰 처리한다.

각 페이지의 canonical은 자기 공개 경로를 가리킨다. `ko`·`en`은 서로 연결하고 `x-default`는 한국어 경로로 정한다. 사이트맵과 언어별 메타데이터는 구현 시 기존 `scripts/sync-search-metadata.cjs` 관리 범위에 추가한다. 기존 게임 카드와 화면 구성은 보존하며 새 카드·언어 전환은 신규 게임 출시 범위에서 검토한다.

### 화면 배치

모바일은 위에서부터 게임명·언어 전환, 남은 기회, 질문 기록, 질문/정답 모드, 입력창·전송 버튼 순으로 배치한다. 질문·정답 모드는 색상 외에도 텍스트와 선택 상태로 구분한다. 기록은 스크롤하고 입력 영역은 모바일 키보드와 하단 안전 영역 위에서 접근 가능하게 둔다. 데스크톱도 같은 순서를 유지하되 기록 폭을 제한해 긴 질문이 읽기 어렵지 않게 한다.

전송 직후 대기 상태를 표시하고 중복 입력을 막는다. 한국어 조합 입력 중 Enter는 전송으로 처리하지 않는다. 새 답변과 남은 기회는 스크린 리더에 알리고 포커스는 입력 흐름을 유지한다. 포기에는 확인창을 둔다. 결과 화면에는 정답, 해당 의미, 사용 횟수, 기록과 다시 하기 버튼을 표시한다.

검사 화면 크기는 360×800, 390×844, 430×932, 768×1024, 1440×900을 기본으로 하고 휴대전화 가로 화면도 포함한다. `safe-area`·동적 뷰포트·키보드 표시·200% 확대를 확인한다. 긴 영어 문구, 한영 혼합 질문, 긴 정답도 잘리거나 가로로 넘치면 안 된다. 문구 원본은 [SCENARIO.md](SCENARIO.md)에서 관리한다.

## 11. 연속 성공 랭킹

기본 순위는 20회 안에 정답을 맞힌 개인 최고 연속 성공 횟수다. 1회 만에 맞혀도 20회째 맞혀도 성공 횟수는 1만 증가한다. 질문 수는 동률을 정할 때만 사용한다. 실패 후 현재 연속 횟수는 0이 되지만 이미 달성한 최고 기록은 남는다.

| 우선순위 | 정렬 기준 |
| --- | --- |
| 1 | 최고 연속 성공 횟수가 많은 순 |
| 2 | 그 연속 기록에서 사용한 질문·정답 제출의 총합이 적은 순 |
| 3 | 위 두 값이 같으면 먼저 해당 기록을 달성한 순 |

예를 들어 7연속·총 65회, 7연속·총 81회, 6연속·총 40회라면 나열한 순서로 순위를 정한다. 동률 비교의 총 기회에는 해당 연속 기록에 포함된 성공 판만 합산한다. 직전 실패 판, 보류·오류·무료 중복 질문은 더하지 않는다. 서버·통신 속도 차이를 고려해 플레이 시간은 순위에 반영하지 않는다.

성공할 때마다 현재 도전의 누적 기록을 비교해 개인 최고 기록을 즉시 갱신한다. 연속 성공 횟수가 늘면 새 최고가 되고 같은 횟수를 다시 달성했으면 총 사용 기회가 적은 기록으로 교체한다. 성공 횟수와 사용 기회는 같은 연속 도전의 같은 시점 값을 함께 저장한다. 다른 도전의 낮은 기회 수를 섞거나 다음 판의 기회를 이전 최고 기록에 더하지 않는다.

| 상황 | 현재 연속 기록 |
| --- | --- |
| 20회 이내 정답 제출 성공 | 1 증가, 다음 판으로 이어짐 |
| 20회 소진·포기·진행 중 문제를 버리고 새 게임 시작 | 종료, 다음 도전은 0회부터 |
| 새로고침·탭 닫기·언어 전환 | 같은 판 복구, 즉시 종료하지 않음 |
| 시작한 판을 24시간 안에 완료하지 않음 | 해당 판 만료로 도전 종료 |
| 성공 후 다음 판을 아직 시작하지 않음 | 유지, 다음 판을 시작할 때 새 24시간 적용 |
| 모델 오류·시간 초과·판정 보류 | 유지, 성공으로도 계산하지 않음 |
| 운영 측에서 확인한 서버 장애 | 장애 시간만큼 만료 시각 연장, 복구 후 같은 판 재개 |
| 일별 정답 목록 교체 | 유지, 진행 중 판은 기존 정답 스냅샷 사용 |
| 현재 목록에 미출제 개념이 없음 | 유지, 새 목록 준비 후 이어서 도전 |

한 플레이어는 한 연속 도전과 한 진행 중 판만 갖는다. 다른 탭이나 게임 시작 요청은 진행 중 판으로 복귀시킨다. 문제를 바꾸려면 포기를 확정해야 하며 쉬운 문제만 골라 성공 기록을 이어 붙이지 못하게 한다. 성공 응답 재전송이나 결과 화면 새로고침으로 횟수가 두 번 오르지 않아야 한다.

실패 후 새 도전을 시작해도 출제 이력은 초기화하지 않는다. 이미 본 정답을 반복해 랭킹 기록을 쌓는 방법을 막는다. 출제 목록을 다 쓴 뒤 다음 날 이어서 성공하면 기존 연속 성공 횟수에 더한다.

한국어·영어는 같은 규칙의 통합 랭킹을 사용한다. 언어 전환으로 기록을 복제하지 않는다. 한영 판정 품질은 출시 기준을 각각 통과해야 하고 규칙을 크게 바꾸면 새 기록 구분값을 부여해 다른 조건의 점수를 섞지 않는다. 주간·시즌 구분과 계정 간 기록 이전은 후속 범위다.

랭킹에는 익명 플레이어별 최고 기록 하나를 올린다. 표시 이름 변경은 같은 플레이어의 이름만 바꾸며 다른 사람의 기록과 합치지 않는다. 브라우저 데이터 삭제로 인증 토큰을 잃으면 기존 기록을 본인 기록으로 복구할 수 없다는 제한이 있다. 서버 검증으로 점수 조작·문제 건너뛰기는 막되 외부 검색이나 다른 사용자의 정답 공유를 완전히 막는다고 가정하지 않는다.

## 12. 비용과 운영 지표

2026-10-28 확인한 Microsoft-Decision-1의 OpenRouter 표시 요금은 입력 100만 토큰당 $0.042, 출력 토큰 무료다. 요청당 전체 입력 1,000토큰, 게임당 20회 호출을 가정하면 `1,000 × 20 ÷ 1,000,000 × $0.042 = $0.00084/판`이다. 같은 가정으로 1만 판의 판정 비용은 $8.40이다. Foundry 직접 이용 시에는 해당 배포의 실제 요금을 별도로 확인한다. [Microsoft-Decision-1 가격](https://openrouter.ai/microsoft/microsoft-decision-1).

이는 견적용 계산이며 실측 운영비가 아니다. 세 가지 판정 항목, 사실 카드, 누적 기록을 포함한 실제 입력량으로 다시 계산한다. 정답 제출은 모델을 호출하지 않지만 보류·재시도는 20회 제한 밖에서도 비용을 쓴다. 한영 생성·사실 검증, Worker·D1 사용료도 별도다. 가격을 바꾸지 않아도 기록이 길어지면 판당 비용이 늘 수 있다.

운영에서는 정답 생성 비용과 플레이 판정 비용을 분리해서 기록한다. 생성된 후보 수, 검증 탈락률, 중복률, 200개 완료 여부, 갱신 지연, 판정 보류율, 정답률, 평균 사용 횟수, 응답 지연을 확인한다. 확률이 높은 오답도 표본 검사 대상으로 삼는다.

한국어·영어 지표는 각각 집계한다. 사용자 질문 원문이나 복귀 토큰을 일반 분석 이벤트에 보내지 않는다. 판정 검토용 질문 기록은 전용 저장소의 보관 기간과 접근 범위 안에서만 취급하며 모델에 전송하는 데이터의 범위를 서비스 안내에 명시한다.

## 15. 개정과 검증 기록

### 2026-10-28 개정

기존 한국어 기획에 한국어·영어 독립 URL, 언어 전환과 세션 유지, 한영 공통 정답 데이터, 언어별 평가·출시 기준을 추가했다. 현재 저장소의 공용 API 주소·D1·Cron·정적 게임 구조를 확인하고 API 경로와 연동 위치를 구체화했다. Jev 버전·가격·판정 API는 위 공식 문서로 다시 확인했다.

같은 날 0.3 개정에서 사용자 의견을 반영해 판정 모델을 Microsoft-Decision-1 우선안으로 변경했다. 개인 최고 연속 성공 랭킹, 총 사용 기회에 따른 동률 처리, 서버 검증·복구·기록 보관을 추가했다. 모델 기능·호출 경로·가격은 Microsoft와 OpenRouter 공식 문서로 확인했고 실제 한영 모델 평가는 아직 수행하지 않았다.

0.4 개정에서는 사용자별 누적 출제 이력으로 기간 제한 없이 재출제를 막도록 변경했다. 매일 준비한 공통 목록에서 미출제 개념만 추려 무작위 순서를 만들고 차례로 배정한다. 개념 ID 유지, 세션 생성 시 사용 완료 기록, 목록 소진·갱신·장애 처리와 익명 ID의 보장 범위를 함께 명시했다.

0.5 개정에서는 고급 탐정 서재를 신규 게임의 디자인 방향으로 정리했다. 봉인 문서와 20개 눈금, 잉크색·아이보리·황동 색상, 한영 글꼴 역할, 화면별 배치·판정 연출·소리·모바일 입력 대응과 에셋 품질 기준을 추가했다. 대표 이미지 시안은 분위기 검토용이며 실제 게임 UI 구현이나 브라우저 검증 결과와 구분한다.

0.6 개정에서는 UI 전용 이미지 에셋과 상태별 제작·검수 기준을 추가했다. 질문·예/아니오·정답 성공·오답·최종 실패·최고 기록의 효과와 사운드 시점을 나누고 기존 블록팡·루멘 시프트 음원 10개를 재사용 후보로 정리했다. 대표 콘셉트 시안은 1672×941 PNG 원본으로 보존했다.

저장소 변경은 기획서와 문구·검토 기록에 한정한다. 콘셉트 이미지와 생성 프롬프트는 로컬 검토 폴더에 따로 보관한다. 실행 코드, 게임 화면, API, 데이터베이스, 스케줄과 배포 설정은 변경하지 않는다. 문서 검사는 [작업 기록](DESIGN_REVIEW_20261028.md)에 남기며 아래 과거 검사 결과를 이번 검사 결과로 취급하지 않는다.

### 이전 기획서에 남아 있던 검증 기록

- 변경 범위: 신규 하위 폴더의 기획서 한 파일. 실행 코드, 기존 화면, 배포 설정 변경 없음
- 공통 기능 검사: `npm run test:shared` 통과
- API 검사: `npm run test:api` 통과
- 전체 검사: `npm test`는 기존 `blockpang/visual-quality.test.cjs:55`의 Game.js 버전 문자열 검사에서 실패. 실제 HTML의 20260917 버전과 검사가 요구하는 20260912 버전이 불일치하며, 관련 파일은 작업 전 HEAD와 동일
- 자산 검사: `npm run assets:check`에서 기존 `asset-manifest.json` 불일치 확인. 이번 변경에 자산 파일이나 자산 목록 변경 없음
- 화면 검사: 포털 1440×1000 데스크톱과 390×844 모바일 전체 화면을 작업 전후 비교해 PNG SHA-256 일치 확인. 양쪽 모두 게임 카드 10개, 가로 넘침과 깨진 이미지 없음
- 빌드 범위: 기획서만 추가하는 정적 문서 배포로 신규 게임 빌드 대상 없음. 전체 테스트 통과나 게임 구현 완료로 기록하지 않음
