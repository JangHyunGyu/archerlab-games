# Zombie defense ranking, sprites and runtime review — 2026-10-04

Ranking submission could remain pending behind a rejected reward-progress command. The client advances its survival clock at 1x, 1.5x or 2x, while the server previously allowed only wall-clock time plus ten seconds. Validation now uses the supported maximum speed as a server-owned ceiling for time, kill/reward pace and stage pace. Impossible time and invalid stage evidence remain rejected.

A verified ranking can proceed past a rejected optional `run_progress` command, but not a rejected stage-clear command. The normal score verifier still runs before insertion. Retained failures of the old time check are revalidated during draining and alarms without changing their payload hashes, allowing later stage commands to recover without the browser. The browser drains multiple 20-command envelopes, including submissions appended during an in-flight batch; completed receipts release their payloads and retain at most 128 in-memory receipts. Offline persistence, response-loss recovery and transactional deduplication remain intact. A completion event refreshes an open zombie leaderboard. Online and offline notices now describe their actual states.

Eight zombie types (runner, teacher, athlete, janitor, guard, charger, crawler and spider) received proportion corrections through built-in imagegen. Four locomotion frames and the established four/eight collapse frames were repainted together per type: 84 distinct poses, 180 runtime cells including repeated walk variants. All walking frames face the viewer. Collapse order, joint poses and final side/prone orientation were reviewed at game size, mirrored and unmirrored. Sources, exact prompts and registration measurements are in `school-zombie-defense/design/source-assets/proportions-20261004`. Generated row spacing is detected from transparent gaps; each pose is registered to its own original bounds, rather than to standing height. Runtime WebP copies use quality 90 with pixel-identical alpha; PNG masters retain full image data. Motion centroids and final bounds were regenerated. Charger final scale changes from 1.15 to 1.16 to retain anatomical continuity.

The crossbow's nine directions and release/recovery frames passed review and existing release-origin/footing tests. Minor direction-dependent skin warmth remains; regeneration was unnecessary for motion continuity.

The dense-horde profile identified repeated front-blocker queries and allocation of temporary foot-point objects. Side-stepping now reuses its existing blocker, and comparison uses scalar foot coordinates. Run cleanup also clears separation candidates that retained dead zombies. Action slice canvases cap their height at 576px, retaining detail for the sub-267px gameplay display at 2x resolution. Chrome `Runtime.getHeapUsage.backingStorageSize` decreased from approximately 539MB to 436MB; this is browser backing storage, not a measurement of GPU VRAM or physical phones. This experiment does not establish an FPS improvement across all devices.

Six browser stress cycles enabled all eight defenders against 80 zombies, then reset. Zombies, bullets, corpses, transient objects, run timers and separation references returned to zero each time. Display-list size excluding the bounded reusable damage-text pool stayed constant; post-warmup heap stayed within the 1.5MB tolerance. Persistent corpses, effects and pooled texts were exercised. All page-error checks passed. The separate 160-zombie profile was used to locate the CPU work. Existing corpse tests cover a 400-death burst.

Nickname controls previously became too narrow in landscape. The layer now uses the full viewport there, and the keyboard-safe viewport updates when width changes while the dialog is open; responsive checks cover 320×568, 390×844, 844×390, 768×1024 and 1440×900. Primary controls keep 44px minimum targets. Keyboard and reduced-motion behavior use the existing flow.
